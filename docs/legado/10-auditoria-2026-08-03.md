#### Grants de RPC endurecidos

Descoberta durante a correção: em Postgres, funções recebem `EXECUTE` para `PUBLIC` por padrão, então o `REVOKE ... FROM anon` da primeira migration **não teve efeito** — `anon` herdava de `PUBLIC`. Foi necessário revogar de `PUBLIC` e conceder explicitamente.

Estado final verificado com `has_function_privilege`:

|--------|:----:|:-------------:|:------------:|
| `log_audit` | ❌ | ❌ | ✅ |

## 1. 🔴 CRÍTICO — Service role key exfiltrável via `/api/evaluate`

**Onde:** `api/evaluate.py`

O avaliador executa o código do aluno com `exec()` **no mesmo processo** do handler, com `builtins` completo. A função `scrubbed_env()` limpa `os.environ` durante a execução, mas as chaves já foram lidas para **variáveis globais de módulo** no import (linhas 22–24):

```python
SERVICE_ROLE_KEY = os.environ.get("SUPABASE_SECRET_KEY") or os.environ.get("SUPABASE_SERVICE_ROLE_KEY", "")
```

Limpar `os.environ` não remove esse valor da memória do módulo. Código do aluno pode alcançá-lo via `sys.modules` e devolvê-lo ao cliente levantando uma exceção cuja mensagem contenha a chave: `_exec_student` captura a exceção, formata como `f"{type(e).__name__}: {e}"`, e isso vira `failureDetails` — retornado ao browser com **HTTP 200**.

**Cadeia completa:** aluno autenticado envia `main.py` arbitrário → `exec` com builtins completo → lê a global do módulo → levanta exceção com a chave → chave chega ao browser em `failureDetails`.

**Impacto:** a service role key **ignora toda a RLS**. Quem a obtiver lê todos os perfis, altera notas e progresso, emite certificados, apaga dados. Qualquer aluno matriculado consegue — não exige privilégio especial.

**Por que as defesas atuais não bastam:**
- `scrubbed_env()` protege só `os.environ`, não globais de módulo.
- `__builtins__ = builtins` libera `__import__`, `open`, `eval`.
- Não há isolamento de processo, usuário ou rede.

**Correções, em ordem de eficácia:**
1. Executar o código do aluno em **subprocesso** (`subprocess.run`) com `env={}` limpo, sem herdar as globais, com timeout e limites via `resource.setrlimit`. Só o subprocesso toca o código do aluno; a chave nunca entra naquele espaço de memória.
2. Nunca devolver mensagem de exceção crua ao cliente: sanitizar `failureDetails`, filtrando qualquer string que se pareça com um JWT/chave.
3. Como mitigação imediata, `del` das globais de chave após uso, ou lê-las dentro da função em vez de no import.
4. **Rotacionar a service role key** — assumir que já pode ter vazado, dado que a plataforma está no ar desde julho.

## 2. 🟠 ALTO — `log_audit` aceita qualquer chamador e qualquer identidade

**Onde:** função RPC `public.log_audit`

```sql
CREATE OR REPLACE FUNCTION public.log_audit(p_actor_id uuid, p_actor_name text, ...)
 SECURITY DEFINER
AS $function$
BEGIN
  INSERT INTO public.audit_log (actor_id, actor_name, action, target, meta, severity)
  VALUES (p_actor_id, p_actor_name, p_action, p_target, p_meta, p_severity);
END;
$function$
```

Não há **nenhuma** verificação de autorização, e a função está exposta a `anon` e `authenticated` via `/rest/v1/rpc/log_audit`. Qualquer pessoa pode inserir entradas de auditoria com `actor_id`/`actor_name` arbitrários — inclusive se passando pelo admin — e inundar a tabela.

Isso é diferente das outras RPCs: `grant_badges`, `reorder_lessons`, `get_lesson_hidden_tests`, `get_lesson_quiz_questions` e `replace_lesson_quiz_questions` **todas checam autorização internamente** e estão corretas.

**Correção:** exigir `auth.uid() = p_actor_id` (ou restringir a `is_admin()`), e `REVOKE EXECUTE ... FROM anon`. Se o log só é escrito por rotas server-side com service role, revogar de `anon` e `authenticated` por completo.

## 3. 🟠 ALTO — O timeout do avaliador não interrompe o código

**Onde:** `api/evaluate.py`, `evaluate_with_timeout`

```python
t = threading.Thread(target=_run, daemon=True)
t.start()
t.join(timeout=timeout_s)
if t.is_alive():
    return None   # devolve 408 — mas a thread continua rodando
```

Um `while True:` do aluno devolve 408 ao browser, porém **a thread continua consumindo CPU** até a instância da função ser reciclada. Várias submissões assim degradam o avaliador para todos. A correção do item 1 (subprocesso) resolve isto de brinde, pois um subprocesso pode ser morto de fato (`kill`).

## 6. 🟡 MÉDIO — Arquivos órfãos do Pyodide em `public/` (auto-hospedagem descartada)

`public/pyodide/v0.25.1/full/` contém `pyodide.js`, `pyodide.asm.js`, `pyodide.asm.wasm` e `pyodide-lock.json`, mas falta `python_stdlib.zip`. Por isso `public/pyodide-worker-v2.js` ainda aponta para `cdn.jsdelivr.net` — e **deve continuar apontando**.

### Correção da recomendação original

A primeira versão desta auditoria dizia que completar a auto-hospedagem era "o passo mais direto para performance do Pyodide". **Isso estava errado.**

`installPackages()` no worker usa `py.loadPackage(native)`, que resolve as URLs dos wheels **relativas ao `indexURL`**. Apontar o `indexURL` para a pasta local — que teria apenas o núcleo — faria os 14 pacotes nativos do catálogo (`numpy`, `pandas`, `matplotlib`, `scikit-learn`, `scipy`, `sympy`, `statsmodels`, `pillow`, `imageio`, `xgboost`, `networkx`, `lxml`, `sqlalchemy`, `pyodide-http`) retornarem 404.

Hospedar os wheels junto significa a distribuição completa. A [documentação oficial](https://pyodide.org/en/0.25.1/usage/downloading-and-deploying.html) é explícita: `pyodide-0.25.1.tar.bz2` passa de **200 MB**, enquanto `npm install pyodide` entrega apenas o `pyodide-core` (o mínimo de boot, com o `python_stdlib.zip`, sem wheels). Não cabe num deploy da Vercel nem faz sentido versionar.

**Decisão:** manter o CDN. O jsDelivr é bem cacheado pelo browser e o núcleo tem ~10 MB.

**Ação recomendada:** remover os 4 arquivos órfãos de `public/pyodide/` (peso morto), e redirecionar o esforço de performance para o que a lista de prioridades original de fato pedia — **reuso do worker entre lições e cache**, que é onde está o ganho real (hoje cada lição reinicializa o runtime do zero).
